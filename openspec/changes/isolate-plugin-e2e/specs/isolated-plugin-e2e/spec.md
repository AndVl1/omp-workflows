# Spec Delta

## Purpose

Обеспечить повторяемые реальные E2E-прогоны плагина omp без смешивания с рабочими плагинами и состоянием пользователя, с контролируемым переиспользованием авторизации и автоматизируемым lifecycle окружения.

## ADDED Requirements

### Requirement: Детерминированная подготовка без участия модели

Harness SHALL предоставлять документированные скриптуемые команды подготовки, диагностики, запуска, остановки, отчёта и очистки. Вход SHALL явно определять источник «установленный omp на момент prepare», набор артефактов плагинов, fixture, сценарий, модель и способ авторизации без значений секретов. Подготовка SHALL возвращать manifest с идентичностями входов, путями окружения, статусом и следующей командой; SHALL поддерживать JSON и ненулевой exit code при отказе. Подготовка MUST NOT требовать LLM, ручного редактирования глобальных конфигов или придуманных агентом команд установки.

#### Scenario: Повторная подготовка
- **WHEN** оператор повторяет подготовку с теми же неизменными входами для существующего подготовленного прогона
- **THEN** harness подтверждает те же артефакты и окружение без переустановки, сброса workflow state или provider-вызовов

#### Scenario: Несовместимые входы
- **WHEN** повторная подготовка того же прогона запрашивает другой runtime, fixture или сборку плагина
- **THEN** harness возвращает явный конфликт и команду создания нового прогона, не заменяя файлы действующего окружения

### Requirement: Стабильная идентичность проверяемой сборки

Каждый прогон SHALL снимать актуальный установленный на момент prepare omp, проверять его compatibility и закреплять автономный runtime вместе с артефактами плагинов и content hashes, включая runtime-зависимости и обнаруживаемые ресурсы. Изменение checkout, глобальной установки или PATH MUST NOT менять код существующего прогона; новая версия omp применяется только к новому run. Harness SHALL переиспользовать проверенные неизменяемые артефакты между прогонами без переиспользования изменяемого состояния. Повреждённый либо неполный артефакт MUST NOT запускаться.

#### Scenario: Пересборка во время теста
- **WHEN** checkout пересобран в сборку B, пока прогон со сборкой A активен
- **THEN** текущая сессия и её дочерние процессы, а также новая сессия того же прогона продолжают использовать A

#### Scenario: Изменение кэша
- **WHEN** проверка обнаруживает несовпадение хеша используемого артефакта
- **THEN** запуск отвергается с диагностикой целостности без обращения к глобальной копии плагина

### Requirement: Изоляция discovery и рабочего состояния

Harness SHALL отделять от host environment home/config, plugin registry и discovery, workspace, temporary files, sessions, logs, caches и workflow state прогона, включая дочерние процессы. Harness MUST NOT устанавливать, обновлять, отключать или перелинковывать глобальные плагины/npm packages и MUST NOT читать host config как overlay. До исполнения сценария SHALL проверяться declared roots, digest доступных ресурсов и фактическое поведение отдельного omp-процесса: контрольные команды из двух разных снимков доступны только в соответствующих runs, а загрязняющие host плагины и их команды недоступны. Доступные native сигналы о загруженных командах SHALL сверяться с этими проверками, но категория источника без пути MUST NOT объявляться полным доказательством происхождения каждого загруженного sibling-ресурса. Необъявленные внешние плагины, дубликаты либо провал контрольной проверки SHALL блокировать сценарий.

#### Scenario: Глобально установлена другая версия
- **WHEN** рабочий omp имеет другую версию workflow-плагина и дополнительные плагины
- **THEN** тест загружает только объявленный набор, а глобальная установка и её конфиги остаются неизменными

#### Scenario: Загрязняющее окружение
- **WHEN** родительская сессия передаёт пути к host plugins/config или settings содержит внешний extension path
- **THEN** harness исключает неразрешённое наследование либо отклоняет конфигурацию до сценария, а не загружает внешний плагин

#### Scenario: Два независимых прогона
- **WHEN** одновременно запущены два прогона с разными артефактами
- **THEN** каждый использует только свои плагины и изменяемое состояние; остановка одного не завершает процессы другого

### Requirement: Явное переиспользование авторизации

Provider-backed прогон SHALL использовать реальную выбранную авторизацию без наследования рабочего профиля тестовым PTY: через внешний нативный broker, selected API-key env либо отдельно подтверждённый оператором managed native broker с текущей host OAuth DB. Managed режим SHALL требовать явный opt-in, закреплять профиль и runtime snapshot, использовать один независимо подтверждённый broker-manager на профиль и никогда не присваивать чужой listener. Harness MUST NOT копировать host auth DB/refresh credentials в run и MUST NOT автоматически вызывать login, token, migrate, regenerate. Native broker MAY создать свой host token file и штатно обновлять credentials; эти эффекты SHALL быть раскрыты оператору. Независимый refresh обычного host omp SHALL отмечаться как неподтверждённая совместимость, а не называться single-flight. Общие quotas и billing не изолируются; отказ broker/provider не разрешает fallback на host profile или mock.

#### Scenario: Реальный вызов без повторного login
- **WHEN** оператор явно выбирает managed broker и сохранённую OpenAI Codex или xAI OAuth авторизацию с совпадающей моделью
- **THEN** harness запускает закреплённый native broker, передаёт тестовому omp только loopback URL/bearer через child environment и проверяет настоящий provider response без изменения глобальных плагинов/config

#### Scenario: Недоступный или чужой broker
- **WHEN** native broker недоступен, отвергает bearer либо его порт занят чужим процессом
- **THEN** readiness возвращает объяснимый отказ без чтения auth DB тестовым PTY, присвоения чужого процесса или подмены mock-ответом

#### Scenario: Cleanup при общем broker
- **WHEN** cleanup одного run проходит при живом shared native broker или другой сессии
- **THEN** он удаляет только run-owned caches/processes; broker и host token file остаются, а отдельный stop требует подтверждённую manager ownership и отсутствие активных клиентов

### Requirement: Контролируемая проверка native OAuth refresh

Harness SHALL предоставлять отдельный явно запускаемый regression-сценарий с синтетическими OAuth credentials, loopback token endpoint и временным credential store. Сценарий SHALL использовать настоящие native broker, AuthStorage, client и SQLite store из закреплённой тестовой зависимости; допускается внедрить synthetic refresh callback через штатный API. Harness MUST NOT менять установленный omp, реальные credentials или production provider allowlist. Результат SHALL указывать native package version и границу component/process integration; MUST NOT объявляться live provider smoke, проверкой unchanged CLI serve либо межпроцессного single-flight обычных omp-клиентов.

#### Scenario: Конкурентное обновление synthetic authorization
- **WHEN** несколько независимых broker clients одновременно запрашивают synthetic authorization после контролируемого перевода записи в native refresh window
- **THEN** один native broker выполняет один refresh для этой волны запросов, все успешные клиенты используют обновлённый access token, а результат сохраняется и доступен после открытия store заново без дополнительного refresh

#### Scenario: Ошибка synthetic token endpoint
- **WHEN** локальный token endpoint возвращает временную ошибку обновления
- **THEN** клиент наблюдает отказ без выдачи устаревшей авторизации; сохранённая credential не заменяется неуспешным результатом и не отключается как при окончательном invalid grant

#### Scenario: Изолированный и воспроизводимый regression
- **WHEN** оператор запускает standalone refresh regression без настоящих provider credentials
- **THEN** сценарий сначала подтверждает действующий access token без refresh, не обращается к реальным провайдерам, очищает временный store/listeners/processes и выдаёт несекретный receipt; отсутствие совместимого Bun/native package приводит к ненулевому отказу, а не пропуску

### Requirement: Отделение прогона от сессии

Один прогон SHALL поддерживать несколько последовательных omp-сессий с неизменной идентичностью runtime/плагинов и сохранённым workspace/state. Выход процесса, отключение клиента и команда остановки сессии MUST NOT автоматически удалять окружение или evidence. Повторный старт SHALL сохранять evidence предыдущих сессий и получать отдельную идентичность сессии. Без явного безопасного завершения прежней сессии конкурирующий старт SHALL отклоняться.

#### Scenario: Resume после закрытия терминала
- **WHEN** первая сессия завершена после сохранённого workflow-этапа и оператор запускает вторую с тем же manifest
- **THEN** вторая сессия видит состояние этого прогона и ту же сборку; первая transcript и receipts остаются доступны

### Requirement: Адресная очистка и сохранение evidence

Очистка SHALL проверять ownership путей и процессов, останавливать только процессы выбранного прогона, сохранять очищенное evidence отдельно от удаляемого окружения и удалять временные credentials/caches с секретами. Повторная очистка SHALL быть безопасной. Неоднозначная принадлежность процесса или выход пути за разрешённые roots SHALL приводить к отказу, а не к broad kill/delete. После аварии SHALL быть доступна та же адресная очистка; сохранение failed workspace SHALL быть явным и не сохранять auth-секреты. Очистка MUST NOT останавливать внешний auth broker.

#### Scenario: Аварийно завершившийся harness
- **WHEN** harness упал, оставив дочерний процесс и временные файлы
- **THEN** очистка по manifest завершает подтверждённо принадлежащие ему процессы, удаляет временные секреты и не затрагивает другую рабочую сессию

#### Scenario: Повторная очистка
- **WHEN** уже очищенный прогон очищают повторно
- **THEN** возвращается успешный статус отсутствия ресурсов, а сохранённый отчёт остаётся доступным

### Requirement: Evidence принадлежит конкретному прогону

Отчёт SHALL ссылаться только на явно зарегистрированные logs/transcripts/receipts выбранного прогона и включать runtime identity, hashes артефактов, результаты process-level проверок изоляции и доступные native сигналы, модель, режим auth без секретов и результат сценария. Harness MUST NOT выдавать частичный список команд за полный loaded inventory и MUST NOT выбирать самый свежий глобальный лог. JSON/stdout, ошибки и экспортируемое evidence MUST NOT содержать API keys, broker tokens, OAuth credentials или bearer tokens терминала.

#### Scenario: Параллельно пишет рабочая сессия
- **WHEN** во время отчёта появился более новый глобальный omp log
- **THEN** отчёт использует только логи выбранного прогона и не включает глобальный файл

#### Scenario: Экспорт после auth failure
- **WHEN** прогон завершился ошибкой авторизации и оператор экспортирует evidence
- **THEN** отчёт сохраняет диагностический код без значений секретов, включая секреты в URL, сообщениях ошибок и session metadata

### Requirement: Исполняемая проверка изоляции

Проект SHALL поставлять повторяемые сценарии проверки параллельных сборок, стабильности артефакта после изменения checkout, перезапуска с сохранением state и отсутствия мутаций рабочей установки. Отдельный явно запускаемый live smoke SHALL выполнять настоящий provider request с переиспользованной авторизацией. Отсутствие credentials или подходящего runtime SHALL отмечаться как невыполненная live-проверка, а не как успешный E2E. Подготовка и проверки без provider calls SHALL запускаться без расхода LLM-токенов.

#### Scenario: Полная приёмка
- **WHEN** оператор запускает документированные isolation и live-smoke команды с валидными prerequisites
- **THEN** команды выдают проверяемые результаты сценариев и scoped evidence без ручной установки плагина в рабочий omp
