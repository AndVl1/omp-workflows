# Spec Delta

## Purpose

Перевести существующие branch-scoped состояния на независимые запуски без потери результатов, ложного продолжения чужой задачи и ручного обслуживания файлов, сохраняя единственный авторитетный источник исполнения.

## ADDED Requirements

### Requirement: Сохранение существующих запусков при миграции

Система SHALL поддерживать импорт legacy root state и feature state, включая нестандартные feature slugs. Миграция SHALL сохранять задачу, классификацию, ветку, историю, прогресс, артефакты и provenance, различать независимые исходные состояния одной ветки и выдавать каждому стабильный canonical run ID. Повторный импорт того же источника MUST NOT создавать второй запуск. Исторические proofs SHALL сохраняться как evidence, но MUST NOT автоматически авторизовать изменённый execution scope.

#### Scenario: Миграция состояния из legacy root
- **WHEN** обнаружено валидное legacy root state с артефактами и без конфликтующего исполнения
- **THEN** оно становится доступным как самостоятельный запуск с сохранённым прогрессом и читаемыми артефактами; ручное перемещение файлов не требуется

#### Scenario: Несколько состояний одной ветки
- **WHEN** обнаружены два самостоятельных feature state одной ветки
- **THEN** оба сохраняются раздельно, не объединяются по имени ветки и не перезаписывают друг друга

#### Scenario: Повторная миграция
- **WHEN** импорт уже завершён и исходный legacy state снова обнаружен
- **THEN** система возвращает существующее соответствие run ID, не откатывает canonical state к старой версии и не создаёт дубликат

### Requirement: Прерываемая и атомарно публикуемая миграция

Миграция SHALL публиковать canonical запуск только после успешной проверки состояния и переноса всех обязательных ссылок на evidence. Ошибка, конкурентное изменение источника или прерывание MUST NOT уничтожать исходные данные либо публиковать частичный запуск. После перезапуска система SHALL завершать либо откатывать собственную незавершённую миграцию идемпотентно, без ручного удаления промежуточных файлов. Неизвестная новая версия формата SHALL отвергаться без перезаписи.

#### Scenario: Прерывание до публикации
- **WHEN** процесс остановлен после копирования части артефактов, но до canonical commit
- **THEN** исходный запуск остаётся восстановимым, частичный target не выбирается для исполнения, а повторная операция штатно восстанавливается

#### Scenario: Прерывание после публикации
- **WHEN** процесс остановлен после canonical commit, но до финального архивирования legacy источника
- **THEN** повторный запуск распознаёт выполненный переход, не импортирует источник повторно и не переключает authority обратно

#### Scenario: Источник изменился во время миграции
- **WHEN** revision или содержимое источника изменилось после проверки и до commit
- **THEN** миграция отклоняется без удаления или перезаписи источника и без частичной canonical-публикации

### Requirement: Миграция не переносит активное исполнение вслепую

Миграция SHALL выполняться только при подтверждённой неподвижности затрагиваемого исполнения. Живые или неизвестно завершённые legacy dispatch SHALL блокировать перенос этого запуска с диагностикой и способом продолжить сверку на прежней совместимой версии. Миграция MUST NOT объявлять их завершёнными или переносить credential в другой scope без проверки. Конфликтующие идентичности и небезопасные пути SHALL отвергаться без выбора случайного источника.

#### Scenario: Старый worker работает во время обновления
- **WHEN** legacy запуск содержит потенциально исполняющийся dispatch
- **THEN** перенос не выполняется; диагностика указывает запуск и необходимость завершить или подтвердить остановку старого исполнения, а не удалить `.active-feature`

#### Scenario: Артефакт выходит за разрешённую область
- **WHEN** legacy reference использует traversal либо symlink за пределы разрешённого источника
- **THEN** перенос отвергается без чтения/копирования внешних данных и без ослабления containment-проверок

### Requirement: Единственный источник после cutover

После миграции все runtime writers, tools и hooks SHALL использовать только canonical run state. Legacy данные SHALL оставаться архивным evidence или входом явного импорта, но MUST NOT снова становиться активным состоянием из-за маркера, времени изменения или отсутствия текущего selection. Пользователь MUST NOT быть обязан синхронизировать два формата.

#### Scenario: Старый маркер остался после обновления
- **WHEN** canonical run существует, но сохранился `.active-feature`, указывающий на legacy источник
- **THEN** инструменты и hooks используют canonical selection, а маркер не меняет выбранный запуск и не блокирует новый

#### Scenario: Несовместимый прежний API
- **WHEN** внешний потребитель передаёт заменённую форму lifecycle-запроса
- **THEN** новая версия отвергает её с диагностикой перехода на новый контракт, а не молча создаёт старое branch-scoped состояние

### Requirement: Согласованность evidence и представлений

Миграция SHALL сохранять разрешимость ссылок на артефакты, checkpoint evidence, slot contributions, документы и доступную observability. Status, reports и visualization SHALL читать мигрированный run по его идентификатору. Отсутствующие исторические необязательные данные SHALL явно обозначаться как отсутствующие; система MUST NOT восполнять их данными другого запуска.

#### Scenario: Просмотр старого результата после миграции
- **WHEN** пользователь открывает отчёт мигрированного запуска с нестандартным feature slug
- **THEN** отчёт и visualization показывают этот запуск и разрешают его сохранённые evidence-ссылки

#### Scenario: Неполный старый event log
- **WHEN** у мигрированного запуска отсутствует часть исторического event log
- **THEN** отчёт отмечает неполноту и не присоединяет события нового запуска той же ветки
