# Spec Delta

## Purpose

Обеспечить согласованный выбор запуска для команд, инструментов и hooks, исключить влияние чужого состояния и защитить общий worktree от конфликтующего исполнения и неверного присвоения асинхронных результатов.

## ADDED Requirements

### Requirement: Единый scope исполнения

Все lifecycle-sensitive команды, workflow tools и hooks SHALL использовать один и тот же выбранный run context. Session binding SHALL поступать из доверенного host adapter, а не из утверждения модели. При отсутствии выбранного запуска операции перехода внутри workflow SHALL вернуть `no_active_run`; создание/выбор запуска через lifecycle ingress остаётся доступным. Исторические состояния MUST NOT автоматически становиться authority для hooks. Общие проверки безопасности и реальные конфликты исполнения SHALL оставаться активными независимо от выбора workflow.

#### Scenario: Новая сессия видит только историю
- **WHEN** в worktree есть старые состояния, но текущая сессия не запускала и не выбирала workflow
- **THEN** история не навязывает workflow-гейты, а попытка изменить workflow без выбора получает `no_active_run`

#### Scenario: Hooks и tools согласованы
- **WHEN** сессия выбрала запуск B при наличии A на той же ветке
- **THEN** dispatch, checkpoint, DoD и status используют B; данные A не разрешают и не блокируют переходы B

### Requirement: Переключение ветки не переносит состояние

Система SHALL различать идентичность запуска и его Git-контекст. Переход с ветки A на B MUST NOT переносить запуск A на B или автоматически продолжать его. При отсутствии конфликтующего исполнения на B SHALL быть возможен новый независимый запуск. Resume/rework существующего запуска SHALL требовать его сохранённый Git-контекст; автоматическое перемещение одного запуска между ветками не входит в контракт.

#### Scenario: Новая задача после переключения ветки
- **WHEN** прежняя работа на A завершена или безопасно отсоединена, пользователь переключился на B и задаёт новую задачу
- **THEN** создаётся запуск B, а состояние и история A сохраняются без ручного удаления маркера

#### Scenario: Возврат к незавершённой работе
- **WHEN** пользователь возвращается на A и однозначно выбирает её незавершённый запуск
- **THEN** resume восстанавливает именно этот запуск без создания нового из имени ветки

#### Scenario: Попытка продолжить на другой ветке
- **WHEN** на B явно выбран запуск, привязанный к A
- **THEN** мутация отвергается как `run_context_mismatch` с указанием требуемой ветки; чтение истории остаётся доступным

### Requirement: Сериализация конфликтующего исполнения

Система SHALL разрешать только один конфликтующий исполнитель workflow в физическом worktree одновременно. Проверка и получение ownership SHALL быть атомарными между процессами и учитывать обычные workflow и активное CTO-исполнение. Завершённая история и безопасно отсоединённый запуск без работающих dispatch MUST NOT удерживать worktree. Запуск с живым координатором другой сессии или потенциально работающими workers MUST NOT молча отменяться, заменяться либо считаться завершённым.

#### Scenario: Гонка двух новых запусков
- **WHEN** две сессии одновременно начинают задачи в одном worktree
- **THEN** только одна получает право исполнения, другая получает `run_busy` с идентификатором владельца и поддерживаемым действием, без частичного второго запуска

#### Scenario: Переход к новой задаче без живых workers
- **WHEN** текущая сессия начинает новую задачу, а её прежний запуск приостановлен и не имеет незавершённых dispatch
- **THEN** прежний запуск безопасно отсоединяется и остаётся доступным для resume, а новая задача получает независимое состояние

#### Scenario: Старый worker ещё не завершён
- **WHEN** пользователь пытается начать независимую задачу при работающем либо неподтверждённо завершённом worker старого запуска
- **THEN** старт получает `run_busy`, а система предлагает посмотреть состояние или продолжить сверку старого запуска вместо удаления файлов

#### Scenario: Обычный workflow рядом с CTO
- **WHEN** в worktree активно конфликтующее CTO-исполнение
- **THEN** новый обычный workflow не получает конкурирующее право записи; завершённый CTO run не блокирует его только из-за сохранённого состояния

### Requirement: Безопасный handover между сессиями

Resume из другой host-сессии SHALL сохранять запуск и существующие worker identities. Передача coordinator ownership SHALL требовать подтверждённого освобождения или отсутствия прежнего координатора. Отсутствие сессии, истечение времени или смерть координатора MUST NOT означать завершение его workers. При неизвестном состоянии исполнения система SHALL вернуть объяснимый конфликт и поддерживаемый путь сверки, без требования ручного редактирования состояния.

#### Scenario: Новый координатор после закрытия старого
- **WHEN** прежний координатор подтверждённо завершён, а новая сессия выбирает тот же запуск
- **THEN** ownership передаётся новой сессии атомарно; существующие pending dispatch продолжают учитываться под прежними идентичностями

#### Scenario: Два координатора одного запуска
- **WHEN** другая сессия пытается захватить запуск с живым координатором
- **THEN** захват отвергается как `run_busy`, не изменяя cursor, capability и действующий ownership

### Requirement: Результат принадлежит исходному dispatch

Асинхронные результаты SHALL связываться с run и dispatch, захваченными при авторизации работы, а не с текущей веткой или последним выбором сессии. Повторная идентичная доставка SHALL быть идемпотентной; конфликтующая или устаревшая доставка MUST NOT менять новый запуск или новую версию rework.

#### Scenario: Поздний результат после смены выбора
- **WHEN** после выбора B приходит результат dispatch из A
- **THEN** результат сверяется только с A либо отвергается по его scope; B остаётся неизменным

#### Scenario: Повтор результата после rework
- **WHEN** приходит результат старой версии переоткрытой стадии
- **THEN** он не завершает текущую версию стадии и не заменяет её артефакты

### Requirement: Восстановление устаревшего выбора без обхода безопасности

Отсутствующий или терминальный session selection SHALL безопасно отсоединяться без удаления истории. Некорректный явный run и повреждённое canonical state MUST NOT подменяться другим запуском. Workflow-owned действия после смены Git-контекста SHALL останавливаться до согласования контекста; движок не обещает остановить произвольный внешний процесс, запущенный вне его контроля.

#### Scenario: Выбор ссылается на отсутствующий запуск
- **WHEN** новая команда обнаруживает устаревшую session-привязку к отсутствующему run и нет execution claim с невыясненным владельцем
- **THEN** привязка отсоединяется с диагностикой, а новая задача может стартовать без удаления маркера пользователем

#### Scenario: Ветка изменилась во время работы
- **WHEN** Git-контекст изменён при активном запуске и приходит следующий workflow-owned dispatch или переход
- **THEN** действие отклоняется с `run_context_mismatch`, старые workers не считаются автоматически отменёнными, а состояние другого запуска не выбирается

### Requirement: Полнота регистрации доверенного host adapter

Публичная регистрация workflow-бандла SHALL требовать `resolveTrustedToolCallActor`, если передан `getSessionController`. Типизированный контракт SHALL отвергать неполную комбинацию; runtime SHALL проверять её независимо от наличия проверки типов у потребителя. Отказ SHALL происходить до установки hooks, публикации владельца и иных побочных эффектов регистрации. Диагностика SHALL указывать недостающий публичный callback и необходимость обновить интеграцию бандла; удаление controller или отключение admission MUST NOT предлагаться как способ исправления.

#### Scenario: Неполная регистрация стороннего бандла
- **WHEN** бандл передаёт session controller без trusted actor resolver, в том числе через нетипизированный вызов
- **THEN** регистрация отвергается с `workflow_registration:missing_actor_resolver`, объясняет необходимость `resolveTrustedToolCallActor` и не оставляет частично зарегистрированных hooks или владельца

#### Scenario: Полная регистрация не выдаёт полномочия заранее
- **WHEN** бандл регистрирует оба callbacks
- **THEN** проверка полноты допускает регистрацию, но каждый защищённый вызов по-прежнему проходит проверки текущей host identity, выбранного run и claim

### Requirement: Обычные инструменты доступны аутентифицированному host без workflow

Подтверждённая интерактивная host-сессия без выбранного запуска и canonical execution claim SHALL получать доступ к обычным `bash`, `write` и `edit`, если действие проходит остальные применимые safety-проверки. Отсутствие workflow MUST NOT само по себе превращать неизвестного caller в доверенного host. Raw `actor`, `hasUI`, параметры инструмента и совпадение только строкового session ID MUST NOT подменять проверку доверенной session identity. No-run разрешение MUST NOT отменять существующий claim либо ограничения выбранного запуска.

#### Scenario: Свежая интерактивная сессия без запуска
- **WHEN** доверенный адаптер подтверждает текущий interactive host, selected run и execution claim отсутствуют, а обычная операция проходит остальные safety-проверки
- **THEN** `bash git status`, обычная запись или редактирование допускаются без предварительного запуска workflow; завершённая история не становится их authority

#### Scenario: Неизвестный caller имитирует интерактивного пользователя
- **WHEN** caller без подтверждённой host identity передаёт `actor: "orchestrator"`, `hasUI: true` либо другой session manager с тем же строковым session ID
- **THEN** эти поля не дают host authority и защищённая операция без независимого разрешения отвергается с диагностикой identity

#### Scenario: No-run разрешение конфликтует с исполнением
- **WHEN** адаптер возвращает no-run разрешение при наличии selected run или canonical execution claim
- **THEN** оно не разрешает обход run/claim-проверок; защищённая операция без надлежащего scope отвергается, а claim и состояние не очищаются

### Requirement: Отказ host admission объясняет причину и безопасное действие

Отказы host admission SHALL содержать стабильный машинный код, понятное объяснение, безопасное следующее действие и сведения, необходимые для репорта без чтения исходников. Диагностика SHALL различать выявленные ошибки интеграции, несовпадение identity/profile/worktree, отсутствие или конфликт controller/claim и необходимость восстановления canonical state. Отсутствующий результат resolver, исключение и несовместимый формат результата SHALL быть различимы. Если причина или контекст не установлены, сообщение SHALL явно сохранять эту неопределённость, а не приписывать её отсутствующему пакету или idle-сессии. Контракт SHALL закреплять смысл кода, а не точную формулировку человеческого текста.

#### Scenario: Resolver не объяснил отказ
- **WHEN** настроенный resolver возвращает `undefined` и существующая проверка admission не находит необходимого разрешения
- **THEN** отказ сообщает, что адаптер не предоставил authority или причину, и предлагает автору бандла проверить host capture и совместимость интеграции

#### Scenario: Исключение и неверный формат ответа различаются
- **WHEN** необходимое разрешение не получено из-за исключения в resolver либо несовместимого результата
- **THEN** сообщение возвращает отдельный код соответствующей причины и направляет к проверке контракта адаптера, не выдавая её за конфликт execution claim

#### Scenario: Пользователь готовит репорт
- **WHEN** пользователь или его агент получает отказ host admission
- **THEN** сообщение позволяет сообщить код, название инструмента, безопасную метку бандла при наличии, версии OMP/core/bundle и известный сценарий вызова; неизвестные значения не выдумываются

### Requirement: Диагностика не раскрывает секреты и не выдаёт authority

Система MUST NOT включать в admission-диагностику сырые исключения, credentials, tokens, capabilities, ownership proofs, содержимое claims, аргументы инструментов или полный host context и transcript; запрос репорта MUST NOT требовать эти данные. Структурированный отказ адаптера SHALL оставаться только диагностикой. Ответ, совмещающий отказ или иной `kind` с actor-разрешением, SHALL считаться несовместимым результатом и MUST NOT выдавать полномочия.

#### Scenario: Исключение содержит чувствительные данные
- **WHEN** адаптер выбрасывает исключение с секретом или фрагментом пользовательского контекста
- **THEN** отказ сохраняет диагностический код и безопасное действие, но не выводит текст исключения или чувствительные данные

#### Scenario: Противоречивый ответ адаптера
- **WHEN** сторонний адаптер возвращает одновременно `kind: "denied"` и `actor: "worker"` либо совмещает другой `kind` с actor-разрешением
- **THEN** результат отвергается как несовместимый и не разрешает запись или исполнение от имени worker либо orchestrator

### Requirement: Диагностика сохраняет независимые основания допуска

Детализация отказов SHALL сохранять существующие правила допуска инструментов. Неаутентифицированный interactive host в ответе host adapter MUST NOT сам по себе отменять независимо подтверждённую native worker authority; ограничения worker scope и вложенной делегации SHALL сохраняться. CTO admission SHALL по-прежнему требовать точного действующего scope и claim. Диагностика MUST NOT вводить общее требование успешного host actor resolver для ранее допускаемых `ask` и `task`, когда их собственные controller/claim/native и прочие проверки выполнены.

#### Scenario: Worker имеет независимое разрешение
- **WHEN** native authority подтверждает worker и его scope, но interactive host adapter не подтверждает этот caller
- **THEN** операция проверяется по worker authority и соответствующим gates, а не отвергается только из-за отсутствия interactive host proof; worker не получает дополнительных прав

#### Scenario: Допущенные ask и task не получают новый blanket-запрет
- **WHEN** `ask` или `task` удовлетворяет собственным условиям допуска и остальным применимым gates, но host actor resolver не возвращает разрешение
- **THEN** отсутствие этого результата само по себе не добавляет новую причину блокировки; существующие ограничения controller, claim, CTO и native delegation сохраняются

#### Scenario: CTO proof относится к другому claim
- **WHEN** предъявлен CTO proof, не соответствующий текущему точному claim или ownership epoch
- **THEN** он не выдаёт CTO authority, защищённая операция без другого допустимого основания отклоняется с объяснением конфликта, а claim не переписывается

### Requirement: Повреждение выбранного run диагностируется как необходимость восстановления

При защищённом tool-вызове, зависящем от уже выбранного run, подтверждённая невозможность безопасно прочитать его canonical state SHALL приводить к диагностике категории recovery и отказу без изменения состояния. Отсутствующий файл, ошибка разбора и недопустимое состояние MUST NOT маскироваться под пустую idle-сессию или рекомендацию только обновить bundle. Сообщение SHALL направлять к штатной проверке и восстановлению либо к репорту, если восстановление недоступно; оно MUST NOT рекомендовать удалять state, редактировать claims или считать неизвестных workers завершёнными. Этот отказ tool admission не заменяет отдельный безопасный lifecycle-переход отсоединения устаревшего выбора.

#### Scenario: Выбранный run отсутствует или повреждён перед вызовом инструмента
- **WHEN** сессия уже связана с run, но перед зависящим от него вызовом state исчез, стал нечитаемым или не проходит проверку
- **THEN** операция получает recovery-диагностику, сохранённые state/claim не изменяются, другой run не выбирается и ошибка не объявляется исправимой одним обновлением бандла

#### Scenario: Ошибка controller не доказывает повреждение данных
- **WHEN** controller callback завершился ошибкой, но необходимость recovery canonical state не установлена
- **THEN** сообщение указывает на сбой разрешения controller/authoritative context и необходимость репорта, не выдумывая повреждение state или отсутствующую установку
