# Spec Delta

## Purpose

Обеспечить согласованный выбор запуска для команд, инструментов и hooks, исключить влияние чужого состояния и защитить общий worktree от конфликтующего исполнения и неверного присвоения асинхронных результатов.

## ADDED Requirements

### Requirement: Единый scope исполнения

Все lifecycle-sensitive команды, workflow tools и hooks SHALL использовать один и тот же выбранный run context. Session binding SHALL поступать из доверенного host adapter, а не из утверждения модели. При отсутствии выбранного запуска операции перехода внутри workflow SHALL вернуть `no_active_run`; создание/выбор запуска через lifecycle ingress остаётся доступным. Исторические состояния MUST NOT автоматически становиться authority для hooks. Общие проверки безопасности и реальные конфликты исполнения SHALL оставаться активными независимо от выбора workflow.

#### Scenario: Новая сессия видит только историю
- **WHEN** в worktree есть старые состояния, но текущая сессия не запускала и не выбирала workflow
- **THEN** история не навязывает workflow-гейты, а попытка изменить workflow без выбора получает `no_active_run`

#### Scenario: Hooks и tools согласованы
- **WHEN** сессия выбрала запуск B при наличии A на той же ветке
- **THEN** dispatch, checkpoint, DoD и status используют B; данные A не разрешают и не блокируют переходы B

### Requirement: Переключение ветки не переносит состояние

Система SHALL различать идентичность запуска и его Git-контекст. Переход с ветки A на B MUST NOT переносить запуск A на B или автоматически продолжать его. При отсутствии конфликтующего исполнения на B SHALL быть возможен новый независимый запуск. Resume/rework существующего запуска SHALL требовать его сохранённый Git-контекст; автоматическое перемещение одного запуска между ветками не входит в контракт.

#### Scenario: Новая задача после переключения ветки
- **WHEN** прежняя работа на A завершена или безопасно отсоединена, пользователь переключился на B и задаёт новую задачу
- **THEN** создаётся запуск B, а состояние и история A сохраняются без ручного удаления маркера

#### Scenario: Возврат к незавершённой работе
- **WHEN** пользователь возвращается на A и однозначно выбирает её незавершённый запуск
- **THEN** resume восстанавливает именно этот запуск без создания нового из имени ветки

#### Scenario: Попытка продолжить на другой ветке
- **WHEN** на B явно выбран запуск, привязанный к A
- **THEN** мутация отвергается как `run_context_mismatch` с указанием требуемой ветки; чтение истории остаётся доступным

### Requirement: Сериализация конфликтующего исполнения

Система SHALL разрешать только один конфликтующий исполнитель workflow в физическом worktree одновременно. Проверка и получение ownership SHALL быть атомарными между процессами и учитывать обычные workflow и активное CTO-исполнение. Завершённая история и безопасно отсоединённый запуск без работающих dispatch MUST NOT удерживать worktree. Запуск с живым координатором другой сессии или потенциально работающими workers MUST NOT молча отменяться, заменяться либо считаться завершённым.

#### Scenario: Гонка двух новых запусков
- **WHEN** две сессии одновременно начинают задачи в одном worktree
- **THEN** только одна получает право исполнения, другая получает `run_busy` с идентификатором владельца и поддерживаемым действием, без частичного второго запуска

#### Scenario: Переход к новой задаче без живых workers
- **WHEN** текущая сессия начинает новую задачу, а её прежний запуск приостановлен и не имеет незавершённых dispatch
- **THEN** прежний запуск безопасно отсоединяется и остаётся доступным для resume, а новая задача получает независимое состояние

#### Scenario: Старый worker ещё не завершён
- **WHEN** пользователь пытается начать независимую задачу при работающем либо неподтверждённо завершённом worker старого запуска
- **THEN** старт получает `run_busy`, а система предлагает посмотреть состояние или продолжить сверку старого запуска вместо удаления файлов

#### Scenario: Обычный workflow рядом с CTO
- **WHEN** в worktree активно конфликтующее CTO-исполнение
- **THEN** новый обычный workflow не получает конкурирующее право записи; завершённый CTO run не блокирует его только из-за сохранённого состояния

### Requirement: Безопасный handover между сессиями

Resume из другой host-сессии SHALL сохранять запуск и существующие worker identities. Передача coordinator ownership SHALL требовать подтверждённого освобождения или отсутствия прежнего координатора. Отсутствие сессии, истечение времени или смерть координатора MUST NOT означать завершение его workers. При неизвестном состоянии исполнения система SHALL вернуть объяснимый конфликт и поддерживаемый путь сверки, без требования ручного редактирования состояния.

#### Scenario: Новый координатор после закрытия старого
- **WHEN** прежний координатор подтверждённо завершён, а новая сессия выбирает тот же запуск
- **THEN** ownership передаётся новой сессии атомарно; существующие pending dispatch продолжают учитываться под прежними идентичностями

#### Scenario: Два координатора одного запуска
- **WHEN** другая сессия пытается захватить запуск с живым координатором
- **THEN** захват отвергается как `run_busy`, не изменяя cursor, capability и действующий ownership

### Requirement: Результат принадлежит исходному dispatch

Асинхронные результаты SHALL связываться с run и dispatch, захваченными при авторизации работы, а не с текущей веткой или последним выбором сессии. Повторная идентичная доставка SHALL быть идемпотентной; конфликтующая или устаревшая доставка MUST NOT менять новый запуск или новую версию rework.

#### Scenario: Поздний результат после смены выбора
- **WHEN** после выбора B приходит результат dispatch из A
- **THEN** результат сверяется только с A либо отвергается по его scope; B остаётся неизменным

#### Scenario: Повтор результата после rework
- **WHEN** приходит результат старой версии переоткрытой стадии
- **THEN** он не завершает текущую версию стадии и не заменяет её артефакты

### Requirement: Восстановление устаревшего выбора без обхода безопасности

Отсутствующий или терминальный session selection SHALL безопасно отсоединяться без удаления истории. Некорректный явный run и повреждённое canonical state MUST NOT подменяться другим запуском. Workflow-owned действия после смены Git-контекста SHALL останавливаться до согласования контекста; движок не обещает остановить произвольный внешний процесс, запущенный вне его контроля.

#### Scenario: Выбор ссылается на отсутствующий запуск
- **WHEN** новая команда обнаруживает устаревшую session-привязку к отсутствующему run и нет execution claim с невыясненным владельцем
- **THEN** привязка отсоединяется с диагностикой, а новая задача может стартовать без удаления маркера пользователем

#### Scenario: Ветка изменилась во время работы
- **WHEN** Git-контекст изменён при активном запуске и приходит следующий workflow-owned dispatch или переход
- **THEN** действие отклоняется с `run_context_mismatch`, старые workers не считаются автоматически отменёнными, а состояние другого запуска не выбирается
