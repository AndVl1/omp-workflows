## Bugs found and fixed during the walk

### 1. `dod-backstop.ts` used hardcoded legacy path (HIGH)

The gate looked for `dod.json` at `.work-state/artifacts/dod.json` — the
single-state layout. With per-feature subdirs (`.work-state/features/<slug>/artifacts/dod.json`)
the gate reported "DoD missing" even when DoD was present and met.

**Fix:** `resolveDoDPath(statePath)` derives the artifacts dir from the
resolved state path. Same shape as `state.ts`'s `resolveState`.

**Discovery trigger:** Walked end-to-end on a real project, slept on the
gate, saw a false BLOCK on a perfectly-valid DoD. This is exactly the
class of bug the original bash `dod-gate.sh` had gracefully skipped
because of the `WORK_STATE_DIR` fallback — and we lost that fallback
in the rewrite.

### 2. `dod-backstop.ts` accepted empty DoD (HIGH)

An empty `dod.json` (`items: []`) passed the gate. The original bash
gate had the same hole (`items.length === 0` is `!pending`).

**Fix:** explicit `if (dod.items.length === 0) block` before
pending check.

**Discovery trigger:** negative-scenario driver #2 wrote `{ items: [] }`
and dod-backstop passed. This is a real foot-gun: a state machine
without enforcement is decoration.

### 3. `src/engine/types.ts` `StageDef` was missing `description`, `roles` (MEDIUM)

The initial port dropped `roles` (consilium stage needs an array) and
left `description` accessible only on `Profile`. Walked `full-feature.json`
consilium and `tsc` failed.

**Fix:** added `roles?: string[]` and `description?: string` to `StageDef`.

### 4. `tsconfig.test.json` (test build) sat next to `tsconfig.json` and was the wrong shape for the test harness (LOW)

Initial `tsc` produced `dist/index.js` first, which depends on
`@oh-my-pi/pi-coding-agent` (not on npm). The test build needs to
exclude `src/index.ts` and `src/commands/*` and only emit `src/engine/*`
and `src/gates/*`. Built `tsconfig.test.json` with `include` narrowed
to engine + gates.

**Affects:** only the test harness. The production build (npm publish)
includes `index.ts` and resolves the peer dependency at install time.

### 5. `package.json` listed `@oh-my-pi/pi-coding-agent` as a regular dependency (HIGH)

The omp runtime package is NOT on npm — it's bundled with the omp
binary. Listing it as a regular dependency broke `npm install` (`ETARGET`).

**Fix:** moved to `peerDependencies: { "@oh-my-pi/pi-coding-agent": "*" }`.
The host runtime provides it at install time.

### 6. `src/engine/minimatch.ts` JSDoc had backticks that confused `tsc` (LOW)

JSDoc comments with `**/*.kt` were parsed by `tsc` as JSDoc-end tokens
because of the surrounding pattern. Cosmetic. Wrote the example in
plain prose.

## What works

- **Workflow data is data.** Profiles, artifact schemas, and
  `.work-state/` files are byte-identical to claude-plugin. The
  migration is non-destructive — anyone with an existing v3.0.1
  install can drop `omp-workflows` in without touching their
  `team-state.json`.
- **Engine compiles cleanly.** `tsc -p tsconfig.test.json` produces
  8 engine modules + 4 gate modules. No `any`, no runtime guards.
- **Monotonic gate works.** Every stage transition keeps the
  monotonic invariant. `state.json` survives a full walk.
- **DoD lifecycle works.** append → close with non-empty evidence →
  gate passes. Empty/pending items block the done-claim.
- **Safety guard works.** `rm -rf /` blocked, `.env` writes blocked.
- **Per-feature subdir layout works.** `.work-state/features/feat-greet/`
  holds state + artifacts. Same shape as claude-plugin.

## What's still untested

- **Task tool integration.** The walker uses the engine directly;
  `callTask` / `task.batch` paths in `src/engine/stage.ts` are stubs
  that need to be wired to omp's native `task` tool. Production runs
  would call `pi.task()` from inside the slash command context.
- **Consilium stages.** `lightweight` has no consilium stage, so
  `applyConditional` + `applyRosterOverrides` weren't exercised. The
  `full-feature` and `standard` profiles path through them.
- **Multi-stage `/team` resume.** Skill suggests long pauses across
  sessions — the per-feature subdir layout supports it, but I
  haven't driven a session_stop → session_start cycle.
- **`/team-yolo` autonomous loop.** Not wired (it needs `hub` + `loop`).
- **Loop stage semantics.** `debug-cycle.json` has a `loop` block
  in `verify` — the engine records iterations but doesn't actually
  re-run `back_to` stages. Documented as a known limitation.

## Coordinator assessment

The engine is **production-ready for the lightweight path**. Five
real bugs found and fixed during the walk. The heavy-presence
profiles (`full-feature`, `debug-cycle`) need the same end-to-end
walk before we ship 0.2.0.

The biggest residual risk is the **TaskCaller integration** — every
production run will go through `pi.task()` / `pi.task.batch()`, and
that's the only path the engine never exercised today. Worth a
dedicated smoke test against the actual omp runtime before tagging
0.1.0 stable.

Sign-off: **OK for internal use, not for external publish** until
consilium + TaskCaller are validated.
