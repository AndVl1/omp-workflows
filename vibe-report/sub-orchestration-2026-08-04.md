# Sub-orchestration (CTO mode) — design plan

Дата: 2026-08-04 · Статус: FINAL (интервью проведено)
Автор: main agent · Репозиторий: omp-workflows-monorepo

## 1. TL;DR

Вводим **CTO/Head-режим** поверх существующего движка воркфлоу: CTO-агент принимает
задачу, декомпозирует её на **команды разработки**, параллельно запускает команды
(каждая — свой sub-workflow из существующих JSON-профилей), собирает результаты,
эскалирует решения на пользователя через **асинхронный адаптер эскалации** и
интегрирует итог. Всё ядро (модель команд, state machine, интерфейс адаптера,
планы, гейты) — в `@andvl1/omp-workflows-core`, чтобы **потребители строили свои
команды и агентов**, не трогая движок. Default-команды (CTO/lead агенты, эталонный
адаптер) — в `@andvl1/omp-workflows-fullstack`.

Ключевое архитектурное ограничение: в OMP 17.x custom-TS команда не может вызвать
`task` — движок исполняется главным агентом как интерпретатором через промпт
(`/do-work` возвращает промпт, агент механически ходит по стадиям). Значит CTO-ядро
должно быть **двухслойным**: (1) чистый TS-движок (план, state, гейты, адаптер) —
вызывается любым потребителем, (2) промпт-контракт, по которому CTO-агент исполняет
план через свой `task`/`hub`. Полный цикл: `run()` → создаёт `TeamPlan` → агент
выполняет `TeamPlan` механически, а TS-движок валидирует каждый шаг (как сегодня
валидирует артефакты стадий).

## 2. Текущее состояние (что уже есть)

| Слой | Что | Ограничение |
|---|---|---|
| `/do-work` (custom-TS) | parseEnvelope → classify → resolveProfile → buildPrompt | Только возвращает промпт главному агенту; `task` недоступен (packages/fullstack/commands/do-work/index.ts) |
| Интерпретатор | Главный агент механически ходит по стадиям профиля через `task` | Интерпретация промптом, не кодом |
| Движок (core) | `engine/{run,stage,state,profile,classify,scope,config}.ts`, `gates/*`, `observability/*` | Библиотека; `run(opts)` вызывается с `taskTool: TaskCaller` — живой вызов возможен только там, где есть TaskTool (главный агент его не держит как API) |
| Stage-типы | `orchestrator` (inline), `single`, `consilium` (параллельные), `bash`, `none` | Нет «командного» типа |
| Pause-кинд | `none, background_wait, user_checkpoint, needs_human, failed, done` | `needs_human`/`user_checkpoint` — **блокирующие** паузы; `background_wait` уже существует, но не описан как канал эскалации |
| Роли/скоуп | `.omp/team.config.json`: `roles`, `scope_map`, `roster_overrides`, `flags` | Уже декларативно; потребитель может переопределить |
| Координатор | `coordinator.md` — read-only, ask-меню; `coordinator-yolo.md` — автономная ночь | Чисто промптовые; не используют `hub`, не имеют CTO-исполнителя |

Пробелы под задачу:
1. Нет сущности «команда»: план декомпозиции, статус команды, владение скоупом.
2. Нет асинхронной эскалации: `needs_human` = жёсткий стоп всей цепочки, ответа вне сессии нет.
3. Координатор не исполняет — предлагает; CTO должен исполнять через `task`+`hub`.
4. Нет канала «продолжай работу, пока пользователь отвечает» (pause `background_wait` не задействован движком).

## 3. Целевая архитектура

### 3.1 Роли (3 уровня)

```
Пользователь
   │  (адаптер эскалации: Telegram / HTTP / push — async)
   ▼
CTO/Head ────────────────► верхнеуровневые координаторы/лиды (lead)
   │  task + hub            │ task + hub
   ▼                        ▼
Команды: [team-kotlin, team-mobile, team-frontend, team-go, …]
   каждая = sub-workflow из существующих профилей (lightweight/standard/…)
```

- **CTO** (новый агент в fullstack): декомпозиция задачи → `TeamPlan` → спавн лидов/команд → сборка → интеграция → DoD → summary. Пишет только `.work-state/cto/<id>/`. Не кодит сам.
- **Lead** (опциональный уровень, см. вопрос интервью Q2): владеет командой, декомпозирует slice на задачи, спавнит воркеров, фильтрует эскалации.
- **Worker** (существующие агенты): однозадачный, без `task`-рекурсии (правило anti-rogue-router сохраняется для воркеров).

### 3.2 Что ложится в CORE (чистый движок, без домена)

```
packages/core/src/
  cto/
    plan.ts          # TeamPlan: decompose(task, scopes) -> teams[]; schema-валидация
    teams.ts         # TeamDef (name, scope, profile, roster), TeamState (per-team)
    escalation.ts    # EscalationAdapter interface + Escalation/Answer типы + файловая очередь
    state.ts         # CtoState: pause kinds, correlation ids, answers/, integration status
    gates.ts         # team-DoD, integration-DoD, escalation-timeout policy
    run.ts           # runCto(opts): create plan -> validate -> persist -> return plan
  commands/cto.ts    # /cto <task> — envelope + промпт-контракт (как do-work)
```

**Интерфейс адаптера эскалации (главный контракт для потребителей):**

```ts
// packages/core/src/cto/escalation.ts
export interface Escalation {
  id: string;            // correlation id: cto-run / team / checkpoint / attempt
  level: "question" | "decision" | "needs_human" | "blocker";
  title: string;         // кратко, без секретов
  body: string;          // sanitized: контекст + вопрос + варианты/дефолт
  options?: Array<{ id: string; label: string; apply: "now" | "on_next_checkpoint" }>;
  default?: string;      // дефолт при timeout
  timeoutMs?: number;    // 0 = без таймаута (ждать вечно)
  replyTo?: string;      // эскалация-родитель (цепочки уточнений)
}

export interface EscalationAdapter {
  readonly kind: string;                 // "telegram" | "http" | "notify" | ...
  send(esc: Escalation): Promise<{ sent: boolean; channelRef?: string }>;
  cancel(id: string): Promise<void>;     // отозвать устаревший вопрос
  // Ответы НЕ через adapter.poll: потребитель кладёт ответ файлом:
  //   .work-state/cto/<id>/answers/<esc-id>.json  { answer, at, by }
  // а движок/агент подхватывает на следующем чекпоинте (устойчиво к рестартам).
}
```

Адаптер — **интерфейс на стороне потребителя**: fullstack поставляет эталонную
реализацию, потребитель регистрирует свою (конфиг + `session_start`/`before_agent_start` hook).

### 3.3 Асинхронная эскалация (команды продолжают работать)

Правило: **эскалация не блокирует всю цепочку**. Три класса:

1. **Локальный вопрос (интерактивная сессия)** — существующий `ask` на чекпоинте; ответ приходит сразу.
2. **Внешний вопрос (адаптер)** — `send()` → команда, ожидавшая ответ, **park** (`pause.kind = background_wait`, state персистится); остальные команды продолжают; CTO продолжает работу по неблокируемым путям. Ответ пришёл → файл `answers/<esc-id>.json` → агент команды будится (hub `send` / poll на следующем чекпоинте) → применяет ответ.
3. **Внешний вопрос + продолжение без ожидания** — команда фиксирует дефолт, продолжает, а ответ пользователя применяется как `apply: "on_next_checkpoint"` (уточнение, а не блокер).

Timeout: `timeoutMs` истёк → применяется `default`, эскалация помечается `expired` (см. риск R5).

### 3.4 Новый stage-тип `team` в профилях

```json
{
  "id": "implementation_teams",
  "type": "team",
  "teams": ["kotlin-backend", "mobile", "frontend"],
  "parallel": true,
  "profile": "lightweight",          // sub-workflow для каждой команды
  "consumes": ["architecture", "clarifications"],
  "produces": ["team_artifacts"],
  "integration": { "stage": "code_review", "on_failure": "escalate_user" }
}
```

Плюс отдельный top-level профиль `cto.json` (см. Q6): discovery → decomposition →
teams → integration → review → summary. Существующие профили не ломаются: `team` —
дополнительный тип, схемы дополняются.

### 3.5 Переработка координаторских промптов на нативные omp-инструменты

| Сейчас (промпт-проза) | Нативно |
|---|---|
| «Delegating heavy code scans only to the OMP scout agent through task» | Уже `task`; добавить `hub` для peer-коммуникации CTO↔лиды↔координатор |
| Координатор «предлагает /team», CTO отсутствует | Новый CTO-агент: `task` (спавн команд) + `hub` (межкомандные контракты, wake parked) + `ask` (локальные вопросы) |
| `needs_human` = стоп | Адаптер эскалации: `send()` + park + continue; wake по файлу ответа |
| Память координатора — файлы | Сохраняется; CTO добавляет `.work-state/cto/<id>/` |
| — | `before_agent_start` hook: инъекция CTO-контракта и регистрация адаптера в сессию |

## 4. Риски и корнер-кейсы

| # | Риск | Митигация / решение |
|---|---|---|
| R1 | **Rogue-router инверсия**: правило «subagent не делегирует» конфликтует с CTO/лидами, у которых по определению есть `task` | Капабилити-скоуп по ролям: `task`+`hub` только у CTO и лидов (frontmatter), у воркеров — нет. Промпт-контракт: CTO/лид делегирует только вниз по своей команде, никогда не поглощает фичу |
| R2 | **Конфликты параллельных команд**: одна ветка (связанные задачи) + раздельные worktree (независимые) | Стратегию владения выбирает CTO в TeamPlan (решение Q3): `worktree`/`branch` per team. Связанные — одна ветка, скоуп-разделение по `scope_map` + контракт «не трогай чужие файлы»; независимые — свои worktree. Интеграция = merge worktree-веток + обязательная integration-review стадия. Разруливание конфликтов — через IRC (`hub`), не через паузу всей цепочки |
| R3 | **Контекстный/стоимостной взрыв**: CTO аккумулирует все артефакты команд; N команд × профиль × модели | В CTO идут только **сжатые сводки** команд (не сырые артефакты); sub-profile по сложности slice (Q5: lightweight/standard); per-team modelRoles; кап **8 команд**; глубина 2; re-plan loop с `max_iterations` + `on_exhausted: escalate_user` |
| R4 | **Утечка через внешний канал**: произвольный чат/пуш = поверхность эксфильтрации | Санитизация эскалаций в движке: только заголовок + обезличенный контекст + вопрос + варианты; секреты/полные файлы/токены запрещены; уровень `blocker` требует подтверждения чувствительности |
| R5 | **Поздний/устаревший ответ**: пользователь ответил, а команда уже пошла по дефолту | Ответы версионируются: `answers/<esc-id>.json` применяется только если команда всё ещё на этом чекпоинте; иначе — `advisory` (логируется в decisions, применяется на следующем чекпоинте как `apply: on_next_checkpoint`); отзыв через `adapter.cancel(id)` |
| R6 | **Таймаут без ответа / автономность CTO** | Лестница (Q4): сначала CTO решает сам (документирует «почему» в decisions). На пользователя уходит только то, что CTO не может решить. `level=blocker`: ждём без таймаута (`timeoutMs=0`), максимум работы продолжается параллельно, команда остаётся parked; `level=question/decision`: `timeoutMs` + `default` → продолжить, поздний ответ = advisory |
| R7 | **Долгоживущие сессии / рестарты**: паркованная команда переживает сон машины, omp restart, компактизацию | Всё состояние — файлы (`.work-state/cto/<id>/`), ответы — файлы; wake = poll на чекпоинте или hub-сообщение после рестарта; адаптер переотправляет pending-эскалации при старте сессии (hook) |
| R8 | **Сбой одной команды** | Изоляция: команда `failed` → остальные продолжают; CTO на integration решает: re-spawn (с причиной из gate), вырезать скоуп, эскалация. Никогда не валит весь CTO-run |
| R9 | **Дубли ответов / повторная доставка** | `esc.id` идемпотентен: второй ответ с тем же id игнорируется (первый выигрывает), пишется в `answers/` с `at` |
| R10 | **Бесконечная декомпозиция** | Макс-глубина 2; `max_teams` кап; re-plan loop с `max_iterations` + `on_exhausted: escalate_user` (уже есть в схеме loops) |
| R11 | **DoD-агрегация**: per-team DoD + интеграционный DoD | Каждая команда пишет свой `dod.json`; integration-стадия требует закрытых team-DoD; backstop-gate расширяется на CtoState (только на done-claim) |
| R12 | **Интерпретатор не умеет TS-вызовы**: CTO-движок в core не вызовется главным агентом напрямую | Двухслойность: движок = валидатор/генератор плана + state-машина (TS, зовётся потребителем), исполнение = промпт-контракт для CTO-агента. `runCto()` возвращает план; CTO-агент ходит по нему механически; артефакты валидируются движком (как сегодня validation gate) |
| R13 | **Hub-коммуникация между агентами** | Только CTO/лиды; формат сообщений — plain prose (контракты — через `local://`/артефакты, не пастой); wake parked — через hub `send` |
| R14 | **Стоимость эскалации для пользователя**: N вопросов от N команд одновременно | Лестница режет поток: до пользователя доходит только то, что не смог решить CTO. Батчинг: CTO собирает вопросы по приоритету (до 1 активного `blocker` на команду); дедупликация по `replyTo`-цепочкам |
| R15 | **Backward compatibility**: существующие профили/агенты/`/do-work` | Новые типы аддитивны; дефолт `type: team` отсутствует в старых профилях — поведение не меняется; CTO-режим включается явно (`/cto` или `cto.json`-профиль) |

## 5. Корнер-кейсы эскалации (детально)

- **Ответ пришёл на отменённый вопрос** (`cancel` уже вызван): файл ответа помечается `stale`, не применяется, логируется.
- **Пользователь ответил частично** (выбрал вариант, но не ответил на follow-up в `replyTo`-цепочке): follow-up переотправляется с пометкой «предыдущий ответ применён».
- **Два ответа в одну секунду на один esc.id**: первый выигрывает (R9).
- **Адаптер недоступен** (нет сети/токена): `send()` вернул `{sent:false}` → движок помечает эскалацию `undelivered`, retry с backoff (до 3 раз), затем — локальный `ui.notify` + `needs_human` pause.
- **Команда ждала ответ, а CTO-сессия уже завершилась**: ответ применяется к `decisions.md`/`answers/` как advisory, ничего не перезапускается автоматически (только с явного `re-run`).
- **Эскалация уровня `question` в autonomous-режиме**: не отправляется (запрещена), применяется `autonomous`-дефолт стадии (как сегодня).
- **CTO-решение вместо вопроса (Q4)**: лид/CTO принял решение сам → запись в `decisions.md` с «почему»; пользователю уходит только уведомление-дайджест (не вопрос).
- **Worktree-интеграция (Q3)**: команда в своём worktree → её ветка merge в основную на integration-стадии; конфликт → IRC-координация между командами (кто владеет файлом), не авто-резолв.
- **8 команд не хватило**: re-plan loop — CTO пере-декомпозирует (укрупняет команды, `max_iterations` кап), `on_exhausted: escalate_user`.

## 6. Этапы реализации (интервью проведено)

1. **Core: типы + схема** — `TeamPlan`, `TeamDef`, `CtoState`, `Escalation`/`EscalationAdapter`, расширение `_schema.json` (`type: team`, `teams[]`), pause kind `escalation_pending` (или reuse `background_wait`).
2. **Core: движок** — `runCto()`, генерация плана из `scope_map`, файловая очередь ответов, timeout-политика, DoD-агрегация, backstop-расширение.
3. **Core: `commands/cto.ts`** — envelope + промпт-контракт (по образцу do-work).
4. **Fullstack: агенты** — `cto.md`, `lead-*.md` (или один `team-lead.md`), ревью `coordinator.md`/`coordinator-yolo.md` на нативные инструменты.
5. **Fullstack: адаптеры** — **HTTP-webhook эталонный** (send-only, быстрый MVP) + **Telegram-референс** (send + приём ответов → `answers/<esc-id>.json`) + hook регистрации.
6. **Демо-профиль `cto.json`** + e2e-сценарий (по конвенции vibe-report).
7. **Тесты**: unit (plan-валидация, timeout, идемпотентность ответов, изоляция сбоя) + e2e через packages/e2e.

## 7. Открытые вопросы (после интервью — к потребителям)

- Формат эскалации в HTTP-webhook: какой payload ждёт потребитель (JSON-схема `Escalation`) — отдаём схему в core.
- Telegram-референс: long-polling или webhook-приём (зависит от окружения потребителя; дефолт — long-polling, работает без публичного URL).
- Где живут команды потребителя: в `team.config.json` (расширение: `teams[]` секция) или отдельный `teams.json` — предлагаю `teams.json` рядом с профилями (декларативные TeamDef).
